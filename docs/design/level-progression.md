# 宙獸等級與成長（P2-12）

機器可讀數值模型：[progression.json](../../Data/_incoming/p2-12-level-proposal/progression.json)。`confirmed` 為使用者已確認規則；主力分配已定案，副手與整數結算仍有待決項目，暫留 `_incoming`。這不是可匯入的宙獸資料，亦尚無正式 progression schema。

## 已確認規則（2026-11-08）

- 個體等級為整數 **LV1–100**；新取得的初始御三家為 **LV10**。
- 只有 **CON／STR／SPI／AGI** 隨等級成長：LV1 為該型態基準值的 **10%**，LV100 為 **100%**，中間線性插值。
- 屬性、基礎抗性、專精百分比與招式威力只隨型態／招式資料改變，不乘等級倍率。戰鬥中的特性與效果修正仍依 [combat.md](combat.md) 處理。
- 每種宙獸分別指定固定解鎖門檻，不在取得個體時隨機擲骰；幼年 → 少年為 **LV20–30**，少年 → 成年為 **LV35–50**，超載為 **LV60–80**，區間含兩端。
- 升級經驗來源為 **戰鬥、收服、任務、BOSS 戰**；經驗需求採 **指數曲線**。
- 進化以**等級取代舊經驗門檻**，仍需要並消耗屬性素材；進化保留個體等級，不重置經驗。

## 四維縮放

```text
L = 個體等級，1 ≤ L ≤ 100
B = 目前型態的基準 CON／STR／SPI／AGI
倍率 = 0.1 + 0.9 × (L − 1) / 99 = (L + 10) / 110
未取整能力值 = B × (L + 10) / 110
```

LV10 倍率為 18.18…%；LV100 保留完整基準能力值。等級先縮放四維，再交給既有 [衍生值公式](derived-stats.md)，不是把最終 HP、射程、CD、移速或閃避率直接乘倍率；衍生值原有底值與上下限仍適用。

現有 `stats` 作為 LV100 基準；每項四維僅在縮放後四捨五入一次（half up），整數公式為 `(B × (L + 10) + 55) // 110`（Q-C28 已定案）。C# 乘法前提升為 Int64；不先把倍率取整為百分比，避免低等級出現額外階梯。允許基準值 0，亦不另設最小能力值。

## 指數經驗曲線（已定案）

每次升級所需經驗採指數成長；累計經驗為各級需求的總和。首級需求 **100 EXP**、成長比 **105/100**（2026-11-08 使用者確認）。

```text
C(L) = ceil(100 × (105/100)^(L − 1))，1 ≤ L < 100
T(1) = 0
T(L) = sum(C(k), k=1..L−1)
```

每級需求由精確比率獨立計算後向上取整，不以已取整的上一級需求再乘 1.05，避免誤差累積。移植時可使用工具預算的整數門檻表，避免執行期浮點冪次造成跨後端差異。

| 等級 | 累計需求 T(L) | 升至下一級 C(L) |
|---|---|---|
| 1 | 0 | 100 |
| 10 | 1,106 | 156 |
| 20 | 3,062 | 253 |
| 30 | 6,246 | 412 |
| 35 | 8,523 | 526 |
| 50 | 19,867 | 1,093 |
| 60 | 33,609 | 1,779 |
| 80 | 92,442 | 4,721 |
| 100 | 248,528 | 滿級，不再升級 |

## 經驗分配

- **按每隻個體權重**分配：出場過的主力權重 **4**，其餘主力權重 **2**；每一權重單位分到相同經驗。例：總經驗 120、兩隻出場、四隻未出場且全員存活，總權重為 16，出場者各得 30、未出場者各得 15（2026-11-08 使用者確認）。
- **中途替換**不清除已出場標記；換下與後來換上的個體，只要曾出場就各以權重 4 計算，不按上場次數重複加權。
- **死亡個體不取得經驗，且移出分母**，由剩餘存活主力依權重重新分配。若全員死亡，所有主力均為 0，不做除法。例：總經驗 120、兩隻曾出場但其中一隻死亡、四隻未出場，存活出場者得 40，未出場者各得 20。
- **每場戰鬥獨立記錄出場資格**，下一場戰鬥重置；收服、任務依各自事件的參與紀錄結算，不直接沿用上一場戰鬥，也不累計整次星球探索。重疊事件各自持有獨立紀錄，避免收服／任務結算清掉尚未完成的戰鬥紀錄。
- 副手可以取得經驗與升級，取代 Q-C10 原「副手不升級、不成長」；副手經驗以所屬主力實得經驗的一半為基準。
- 副手是一隻各得一半或副手組均分一半、是否另外發放，以及整數餘額處理仍在 Q-C30 收斂。
- 經驗成長不等於自動進化；進化仍只在大廳執行且檢查素材。副手換型態後，必須重新驗證「副手階段 ≤ 主力階段」，不得沿用「副手不成長所以搭配永遠成立」的推論。

```text
E = 該事件的主力經驗總量
w(i) = 死亡時為 0；存活且曾出場為 4；其餘存活主力為 2
W = sum(w(i))
主力 i 經驗 = W > 0 時 E × w(i) / W，否則為 0
```

`allocate_main_xp` 使用精確分數，保證有存活主力時總額等於 E、每份權重取得相同經驗；在整數結算規則未定前，不逐隻四捨五入或丟棄餘額。這是數值參考輸出，尚不代表存檔可儲存分數經驗。

## 實作交接

- `OwnedCreature.Exp` 需作為累計升級經驗；等級應由同一門檻表推導，避免存檔同時存入不同步的等級與經驗。御三家 LV10 的最低累計經驗為 T(10)。
- `CreatureDef`、creature schema、importer、`EvolutionRequirement`／`EvolutionCheck`／`EvolutionRules` 同步從經驗門檻改為等級門檻，並驗證各進化階段的解鎖區間；不得只改 JSON 讓舊執行期將等級誤讀為經驗。
- `PartnerLoadout.FindInvalidPairs` 現在只重驗關係邊，並假設副手不成長；需更新契約與測試，讓副手進化後也能回報階段超過主力的配對。
- `EventParticipation.record_entry` 以個體 ID 去重，換下不移除；以結算當下死亡狀態呼叫 `allocate`。`reset_event` 只在該事件已結算後清除出場旗標，不改死亡狀態；同時存在的戰鬥、收服與任務不得共用同一份紀錄。
- 參考工具：`python tools/balance/level_progression.py` 輸出完整整數門檻表；`--xp 1106` 驗證 LV10。測試：`python -m unittest discover -s tools/balance -p test_*.py`。
